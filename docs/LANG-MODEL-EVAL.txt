Evaluating AI for Financial Document Extraction: A Practical Case Study
Or: How to Stop Chasing Benchmarks and Start Solving Real Problems

📋 Executive Summary
This case study documents the process of evaluating AI models for extracting financial transaction data from PDF bank statements. The goal was not to find the "best" model, but to determine whether any model could reliably extract data for tax reporting purposes.

What started as a simple question ("Can AI convert my PDFs to CSV?") evolved into a sophisticated evaluation framework. The key insight: domain knowledge and practical requirements must drive AI evaluation, not generic benchmarks.

🎯 The Problem Statement
Business Need
Extract financial transaction data from 12 months of PDF bank statements for tax reporting. The extracted data must be accurate enough to:

Categorize expenses (business vs. personal)

Support tax deductions

Survive IRS audit scrutiny

The Data
Source	Format	Purpose
Bank PDF Statements	PDF	Official record, human-readable
Bank CSV Export	CSV	Machine-readable, limited history
Extracted Output	CSV	AI-generated, to be verified
The Challenge
The PDF and CSV are two different views of the same data, not one derived from the other. This means:

Columns don't map 1:1

Reference numbers don't match

Descriptions are formatted differently

🔍 The Evaluation Journey
Phase 1: Initial Assumptions (Wrong)
Assumption	Reality
"I'll just compare PDF row to CSV row"	❌ Schema mismatch
"Reference numbers should match"	❌ Different systems
"I need exact field-by-field accuracy"	❌ Overkill for the use case
Phase 2: Discovering What Actually Matters
After analyzing the data, we identified the critical fields:

Field	Why It Matters	Match Method
Posted Date	Determines tax year	Exact match
Amount	Determines deduction value	Numeric (±$0.01)
Payee	Determines categorization	Substring/First word
Reference	Traceability	❌ SKIP - doesn't match
Phase 3: Building the Right Test

📊 The Evaluation Framework
1. Dollar-Weighted Accuracy
Traditional accuracy treats all transactions equally:

text
Traditional Accuracy = Correct Transactions / Total Transactions
For tax purposes, this is misleading. A $5,000 missed transaction is far more important than a $5 missed transaction.

Instead, we use dollar-weighted accuracy:

python
def dollar_weighted_accuracy(pdf_rows, extracted_rows):
    total_actual = sum(row['amount'] for row in pdf_rows)
    total_extracted = sum(row['amount'] for row in extracted_rows)
    dollar_drift = abs(total_actual - total_extracted)
    accuracy = (total_extracted / total_actual) * 100
    return {
        'dollar_drift': dollar_drift,
        'accuracy_pct': accuracy,
        'tax_impact': dollar_drift * tax_bracket
    }
2. Acceptance Thresholds
Metric	Green (OK)	Yellow (Review)	Red (Fix)
Dollar drift	< $100	$100 - $500	> $500
Missed transactions	0	1-2	> 2
Amount mismatches	0-2 small	1-2 medium	Any large

text

✅ "Does this AI extract date, payee, and amount correctly?"
Don't chase benchmarks. Chase your specific problem.

Lesson 2: Ground Truth is Not Always Obvious

Before designing a test, understand the data pipeline.

Lesson 3: Test What Matters, Not Everything
For tax reporting:

Nice to have: Full description, Reference number

Don't care: Address, Merchant location

Cut through the noise. Identify the 20% of fields that give 80% of the value.
